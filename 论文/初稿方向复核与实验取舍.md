# 初稿方向复核与实验取舍

复核依据：`总览.jpg`、`后续论文流程.docx`中的师生讨论、初始审计基线`GriddingMachine.jl wyujie@7152680`和`GriddingMachineDatasets wyujie@51cf0fe`，Windows/macOS原始实验提交`53bb0be`和`3926ae3`，以及公开候选提交`11631d6`、`5eac56a`和研究仓库实验冻结提交`8a23b5a`。

## 1. 结论

论文继续以“2022版GriddingMachine的框架更新与验证”为主线，方向正确，但不宜把文章写成泛化的FAIR数据平台论文。老师在讨论中反复强调的是数据怎样制作、发布、更新、下载和用于模型，因此论文贡献应收敛为三个闭环：

1. **新数据进入系统**：模板或配置构建器生成YAML，流水线把异构NetCDF转换为标准NetCDF，完成检查、上传、目录登记，并让新贡献者依据文档重复该流程。当前没有独立客户端。
2. **标准数据可靠到达本地**：取消外层`tar.gz`，YAML目录独立更新，一个标签登记多个镜像，下载先进入cache，校验大小和SHA-256后再进入public；Collector公共操作具有自动回归测试。
3. **本地数据进入模型**：`read_LUT`演进为`read_dataset`，并由`grid_dict`和`grid_weather`组织Emerald初始化所需的陆地参数与气象驱动。

论文围绕数据生产、质量控制、目录与分发、统一读取和模型数据接口组织完整证据链。

## 2. 初稿需要纠正的地方

### 2.1 YAML不是独立创新点

TOML改为YAML主要改善目录可读性和嵌套表达，老师明确称其为“小事情”。正文可以说明它支撑多URL和共享配置契约，但不能把格式替换本身写成核心贡献，也没有必要进行TOML与YAML的性能比较。

### 2.2 论文release不能等同于当前代码快照

初始审计时代码仍缺少老师要求恢复的SHA校验；配置构建逻辑含硬编码保存路径、遗留`TARBALL`字段，并缺少当前流水线所需的部分字段；发布脚本和自动测试也不完整。论文把该commit作为审计基线，把修复并测试后的不可变release作为最终实验对象。未进入release的功能不得写为结果。

### 2.3 “完整Emerald模拟”不是当前核心目标

老师要求`grid_dict`提供模型初始化数据、`grid_weather`提供气象驱动。必要证据是字段数值正确、单位与长度正确，并能完成固定格点的Emerald初始化或最小步进。没有必要把完整科学模拟、参数敏感性或模型性能评估扩展为本论文任务。

### 2.4 缺少贡献流程的独立复现验证

老师明确提出把流程交给岳云熙、陶晨飞或新成员，确认其能按步骤完成。该内容可以放在补充材料或网站，但论文至少应报告：参与者是否无需口头干预完成YAML生成、数据处理、检查、上传模拟和目录登记；在哪一步出错；文档据此怎样修订。它比单纯增加更多性能重复次数更贴近论文贡献。

### 2.5 Collector回归测试覆盖不足

讨论中点名`update_database!`、`download_dataset!`、`sync_database!`、`clean_database!`、目录树和信息查询等逻辑。当前初稿重点测试下载故障，却没有把这些公共操作列成完整回归矩阵。必须补充本地目录已有/缺失、远端目录相同/更新、单标签/全库同步、旧文件清理和信息查询等状态转换。

## 3. 实验取舍

| 实验 | 决定 | 理由与最小规模 |
|---|---|---|
| 合成NetCDF生产正确性 | **保留，核心** | 直接验证老师要求的`lon-lat`、`lat-lon`及二维/三维转换；用代表性组合覆盖关键分支，不以案例数量作为贡献 |
| YAML配置构建器契约测试 | **新增，核心** | 验证构建器生成的YAML能被流水线直接解析和运行；必须移除`TARBALL`及硬编码路径不一致 |
| 新贡献者按文档复现流程 | **已完成单案例** | P01在1次说明后完成受控数据集并通过自动验收；报告干预点，不做泛化用户研究 |
| `.nc`与`tar.gz`效率比较 | **保留，降为支持实验** | ELEV和LAI两个内部压缩样本足以支持“减少额外步骤”的限定结论；不要求ERA5大文件 |
| Collector公共接口回归 | **新增，核心** | 覆盖update/download/sync/clean/tree/info和`read_dataset`，验证状态转换及向后兼容 |
| 多镜像、缓存、SHA及故障注入 | **保留，核心** | Windows与macOS受控矩阵验证失败状态，Ubuntu CI检查兼容性；校园网必须实际只读访问FTP和Zenodo，比较ping顺序、下载时间与内容哈希 |
| 多镜像真实网络大量重复 | **缩减** | 镜像性能随时间和地点变化，3～5个标签每种网络3～5次即可说明外部行为，不外推全库 |
| `grid_dict/grid_weather`金标准 | **已完成，核心** | 受控夹具验证边界行为；真实`gm2`与2020年8类ERA5在US-NR1完成8784步逐点核对和Emerald首步 |
| 完整Emerald长期模拟 | **删除** | 超出框架更新论文问题；改为初始化成功和最小步进烟雾测试 |
| 代码行数和人工调用数比较 | **删除或仅作附录描述** | 定义主观、可重复性弱，不能替代数值正确性；贡献流程复现更有说服力 |
| TOML与YAML格式性能比较 | **不做** | 格式选择不是科学贡献，目录规模下意义有限 |

## 4. 修订后的研究问题

- **RQ1 数据生产与贡献复现**：配置构建器生成的YAML和处理流水线能否把代表性二维/三维异构NetCDF正确转换为标准数据，并使未参与开发的贡献者按文档完成数据登记？
- **RQ2 数据分发可靠性**：直接NetCDF、独立目录、多镜像、缓存和SHA校验能否在Windows与macOS受控故障下保持下载内容和正式目录状态正确，并在Ubuntu CI中保持核心路径兼容？
- **RQ3 公共接口稳定性**：Collector目录管理操作与`read_dataset`重载能否在本地/远端不同状态下得到确定结果，并保留必要的旧接口兼容性？
- **RQ4 模型初始化接口**：`grid_dict`和`grid_weather`能否在受控夹具中生成符合接口约定、可用于Emerald固定格点初始化和最小步进的数据？

## 5. 软件改动执行状态与剩余门槛

下列软件改动已在本地论文分支完成并通过自动测试：目录`SIZE/SHA256`生成与下载后校验；全部镜像失败及残留cache隔离；Windows ping解析与FTP/Zenodo候选排序；共享YAML schema、移除`TARBALL`和可配置输出；二维/三维源维度映射、最小端到端生产、六类缺失值策略、配置对象可重复使用及经纬度方向正确绘图；Collector、`read_dataset`、`grid_dict/grid_weather`回归；Emerald最小初始化与60 s单步。当前通过数为GriddingMachineDatasets 73项、GriddingMachine 63项、Emerald烟雾5项。

剩余投稿硬门槛不是继续堆功能，而是完成证据：

1. P01受控贡献流程已在1次说明后完成；若要声称修订版指南可无帮助完成，再由新参与者复核。
2. 在中科大校园网实际访问FTP与Zenodo，完成ping、两端下载、耗时及`SIZE/SHA256`核对。
3. 锁定论文代码提交和依赖来源，归档原始日志、实验数据哈希和环境信息。
4. 作者确认题名、单位、邮箱、基金、其他作者及作者贡献。

Windows、macOS和Ubuntu的公开核心CI已经完成；2020年真实ERA5单站点链路也已完成。Linux上的真实数据复跑、多站点多年份气象验证、历史YAML全量迁移和原始产品重建均为后续扩展，不是本文“软件更易用、更可靠、可流程化”结论的硬门槛。当前数据产品的数值与缺失值处理按`test/preparation/griddingmachine-v04/catergory.txt`验收。
